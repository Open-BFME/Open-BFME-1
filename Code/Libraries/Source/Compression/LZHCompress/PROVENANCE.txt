One inconsistency is upstream's own and is left as found: Huff.cpp's banner says
"LZH-Light algorithm implementation v 1.01" while Lz.cpp's says "v 1.0". The
repo, this file and the `vendored=lzhl-1.0` tag all say 1.0, after the release
and the directory, not after Huff.cpp's banner. Nothing here depends on which
banner is right — the release is pinned by the commit hash above and by the
3,104 bytes of table data below, neither of which the banner touches.

Why the initial commit and not the branch tip
---------------------------------------------
`main` carries four post-import commits, each of which is a change to the 1998
code rather than a different vintage of it: an INT32/UINT32 retype for LP64
hosts, two POSIX-socket edits to Lzhl_tcp.cpp, an include-case fix, and a
bounds fix that adds `- LZMATCH` to four `_updateTable` calls inside
LZHLCompressor::compress. Only the initial commit is the release. The two are
distinguishable in the one place the bounds fix lands: compress compiles to
1,741 bytes from the initial commit and 1,747 from `main`. Everything else this
tree claims is identical under both, so that single body is the whole
difference — and, as recorded below, neither figure is retail's.

Why this program and not one of the forks
-----------------------------------------
LZH-Light emits no strings, so there is no "assembler version 4.09.00.1126" to
read out of the image the way vendor/d3dx9 could. The discriminator here is
static DATA. Huff.cpp's four `.tbl` files are compiled into seven initialised
arrays, which land in retail's `.data` as five contiguous blocks, byte for byte,
each block at exactly ONE address, in the order the compiler emits them.

Addresses below are VIRTUAL ADDRESSES (imagebase 0x400000), NOT the RVAs the
ledger uses — read as an RVA, 0x012C51E0 is past the end of the image. Both are
given so neither reading can be guessed at:

The three-way split of the first COMDAT is arithmetic, not assertion:
NHUFFSYMBOLS is 274 and HUFFINT/HUFFUINT are 16-bit (_huff.h:25-27), so
274*4 + 16*8 + 274*2 = 1,772 exactly, and each sub-block reads back at its
offset as the matching .tbl: (7,0x14),(8,0x30),(8,0x31) at +0, (2,0),(3,4) at
+1096, 256,257,258 at +1224.

3,104 bytes of Huffman tables, unique in a 20 MB image. On top of that, 31
whole function bodies from these two TUs reproduce retail exactly, 4,310 bytes
at 31 distinct addresses inside one contiguous run. (This paragraph read "26 ...
at 26 distinct addresses" until 2026-08-17: it was written mid-wave and never
refreshed when the last five bodies landed in the same commit. The ledger is
the count of record — `grep -c 'vendored=lzhl-1.0' reverse/functions.csv`.)

Region
------
RVA 0x008252C0-0x00826F9C. The bounds are witnessed, not assumed: zlib's
`_inflateSyncPoint` ends at 0x008252B5 below it and zlib's `_adler32` starts at
0x00826FA0 above it, both already attached from Compression/ZLib. LZHL is the
only thing between them, which is what Compression.dsp says the static library
contains.

Where the files sit
-------------------
`Code/Libraries/Source/Compression/LZHCompress/CompLib{Header,Source}` is EA's
own layout for this library, read out of the Zero Hour Compression.dsp file
list. Upstream ships all fourteen files flat (the nine taken here plus Lzhl.cpp,
Lzhl_tcp.cpp, lzhl.h, Lzhl_tcp.h and Test.c); splitting them across the two
directories is why each .cpp carries
`-ICode/Libraries/Source/Compression/LZHCompress/CompLibHeader` on its `// cl:`
line. `/DNDEBUG` is load-bearing (these bodies carry no assert). `/MD` is NOT:
no body claimed here calls the CRT, so it is byte-indistinguishable, and it is
on the line only to match the zlib TUs that share this static library and are
known to need it.

Only Huff.cpp and Lz.cpp are vendored. Lzhl.cpp and Lzhl_tcp.cpp are in EA's
file list but carry no row here, and `build.py`'s `verify_source_claims`
refuses a row-less `Code/**/*.cpp` — so vendoring them would break the gate to
add nothing. Their headers (Lzhl.h, Lzhl_tcp.h) are left out for the same
reason: nothing this tree compiles includes them.

The ledger contract
-------------------
Rows sourced here carry `vendored=lzhl-1.0` and name the upstream's own
identities. There are no `gen-` names among them. `./build.sh <TU>` compiles
the vendored source and byte-compares each row against retail exactly as it
does for code this repo wrote; a row is not evidence of anything until it
passes that.

What this evidence does NOT decide
----------------------------------
1. Two bodies REFUSE to match, and this release is not BFME's for them.
   LZHLCompressor::compress compiles to 1,741 bytes (1,747 from `main`);
   retail's body at 0x00825680 is 1,724. LZHLDecompressor::decompress compiles
   to 852; retail's callable body at 0x00826920 is 824 bytes (the 844-byte
   unclaimed run begins in its preceding alignment pad). Both stay as
   `Code/gen_asm` dumps. The differences are small and one-directional — EA's
   copy is SHORTER in both — which reads like a local EA edit to the two
   biggest functions rather than a different vintage, but nothing here
   establishes what the edit was, and no attempt was made to guess it. That
   is 2,568 bytes this file explicitly does not claim.

2. `?_wrap@LZBuffer@@KAHI@Z` and `?_distance@LZBuffer@@KAHH@Z` compile to the
   same ten bytes, and exactly two unclaimed addresses in the run hold those
   ten bytes: 0x00825410 and 0x00825420. Counts agree, so both are certainly
   there, but nothing decides WHICH is which — no relocation, no caller that
   distinguishes them, no independent name. Following the standard
   vendor/d3dx9 set for its twins, neither is claimed rather than have the name
   column assert an identity the image does not witness. 20 bytes.

3. `??1HuffStat@@QAE@XZ` is ten bytes and retail holds eleven copies of them,
   spread from 0x00061BD0 to 0x00589A70 with most already claimed by other
   sources. Ten bytes of `delete[]` through the vector-deleting stub is not a
   fingerprint; nothing attributes any of those eleven to this TU, so none is
   claimed.

4. The mangled names in the ledger come from THIS source, not from the image.
   lotrbfme.exe exports none of these symbols and carries no RTTI for them, so
   the C++ type encoding inside a name is the vendored header's, not retail's.
   The `main` branch's `signed int` retype changes
   `?_updateTable@LZHLCompressor@@AAEKKPBEKH@Z` to `...@AAEIIPBEIH@Z` without
   moving one byte of code — proof that the byte claim and the name are
   independent, and that only the byte claim is evidence.
