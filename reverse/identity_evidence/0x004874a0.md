# 0x004874A0 createWindow: signature correction

The ledger carried Zero Hour's 13-argument `createWindow(char*, Int id, Int status, Int x, Int y, Int w, Int h, WinInstanceData*, void*, 4 callbacks)`. The method is the same, but the BFME signature is not.

- **Identity:** the body is the ZH `GameWindowManagerScript.cpp` createWindow. It reads the parent with peekWindow (0x012F24F4 against 0x012F24F8). It compares the type against `"USER"` (0x010F9204) and `"TABPANE"` (0x010F91D8), and ORs GWS_USER_WINDOW 0x200 or GWS_TAB_PANE 0x4000 into the instance style (+0x0C). Any other type goes to createGadget (0x00486B10). It then stores the four edit-data callback strings (0x012F2570..0x012F257C), calls setWindowText (0x004864E0) with the text label (instData+0x188), and sends message 0x16 (manager slot +0xD8) to the parent.
- **Callers:** only parseWindow (0x00487F80), with direct calls at +0x3F9 and +0x51F.
- **ABI:** retail uses MSVC 7.1's private internal-linkage register convention. The type arrives in EDX and the window record in EBX (parseWindow loads EBX=0x012F253C and stores &instData at record+0x30). The id and data arrive on the stack in that order, and the caller cleans up. BFME moved status, position, size and callbacks into that record, and winCreate (slot +0x74) takes the record whole.
- **New name:** `?createWindow@@YAPAVGameWindow@@PADHPAVOpen2479440Record@@PAX@Z`, which is `createWindow(char *type, Int id, Open2479440Record *record, void *data)`. The stack order (id before data) is byte-proven. Where the two register parameters sit in the list is not: (type,id,record,data) and (type,id,data,record) compile identically. The ZH relative order is kept, since the instance data this record now carries came before data there.
