# View's +0x80 marker list at 0x0045C870..0x0045CA80

Commit 60e33af821 renamed `Rva0045C9E0CameraMarkerList` to `CameraMarkerList`
and dropped the address token, inventing an owner class retail contradicts.

**The list lives in View.** ScriptActions::doMoveCameraTo (0x002F24F0, matched)
loads ECX from `?TheTacticalView@@3PAVView@@A` (0x012F1600) at +0x22 and calls
ILT 0x00036A43 -> 0x0045C9E0 at +0x2B with no adjustment; 0x0045C9E0 reads
`[ecx+0x80]`. So the callee is a non-virtual member of TheTacticalView's own
object, not of a separate list class. The matched View constructor
??0View@@QAE@XZ (0x0045B8C0), which installs ??_7View@@6B@ (0x010F6940), zeroes
+0x80 itself (`mov [eax+0x80], ecx` at +0x7F), and the W3DView constructor
0x00745B10 places its second base at +0xB4 right after the View base call, so
View spans +0x00..+0xB3 and +0x80 is View's own member, not W3DView's.
0x0045C8A0 is reached from 0x0045CB70 with the same `this` (ESI=ECX), which
W3DView::reset (0x0073AC90) calls on its unadjusted `this` beside View-range
resets (+0x74, and 0x0045C1D0's +0x0C..+0x78 stores).

**The members.** 0x0045C9E0 (find by AsciiString), 0x0045C8A0 (pop and delete
every node), 0x0045CA80 (unlink and delete the node with a matching name) and
0x0045C8F0 (splice a replacement in place of the node with a matching name,
returning the displaced one) all walk the same singly-linked list whose head is
`[this+0x80]`, with `m_next` at node +0 and an AsciiString at node +4.
0x0045C870 is that node's scalar-deleting destructor: it calls ILT 0x00028984
(-> 0x0045C490, `add ecx,4; jmp` the AsciiString release), the same ILT
0x0045C8A0 and 0x0045CA80 call before `operator delete`.

**Why address tokens.** Nothing names these methods or the node type:
0x0045C8F0, 0x0045CA80 and 0x0045C870 have no named caller, and
doMoveCameraTo only proves that the node's Coord3D at +0x08 is a camera target
and that the node is View slot 24's second argument. So the owner becomes the
proven `View`, each method keeps its address (`findMarker0045C9E0`,
`clearMarkers0045C8A0`, `removeMarker0045CA80`, `replaceMarker0045C8F0`), and
the node type becomes `Rva0045C9E0CameraMarker`, the name the existing ILT
0x00028984 destructor pin already used. The second pin on that ILT,
`??1CameraMarker@@QAE@XZ`, is the same destructor under the invented name and
is retired.

Every body keeps its exact range and is re-probed byte-exact under the new name;
doMoveCameraTo no longer needs a `reinterpret_cast` from View to reach 0x0045C9E0.
