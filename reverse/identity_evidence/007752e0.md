# RVA 0x007752E0 probability record parser

The 308-byte retail body has an SEH entry and returns at +0x133. Its original callback/owner identity remains unknown. The address-qualified callback keeps that provenance. It appends an eight-byte record to the vector at the second argument +0x10. The record contains an owning ASCII string and an integer probability: token `prob` enables the 1..100 range check; otherwise the integer is -1. The separator pointer is reloaded from INI+0x41C for each token call.

Two call contracts are established independently of the caller match:

* At caller +0xED, ILT 0x0001FA1E routes to 0x00768C40 (79 bytes). It is cdecl(destination, const source reference). The non-null destination arm calls StringBase<char> copy construction at 0x00887B60 on word zero and copies source+4 to destination+4. Thus the record is nontrivial owning-string/integer storage, not two ObjectID enums. No original record type name is asserted.
* At caller +0x10D, ILT 0x00022AF7 routes to 0x00771870 (268 bytes). It is thiscall(position, const element reference, type tag reference, count, atEnd), returning with ret20. Its vector fields are +0/+4/+8, allocation and loops use eight-byte elements, all copy phases call 0x00768C40, and cleanup calls 0x007706D0. That cleanup walks elements in eight-byte steps and destroys each before freeing storage. Existing ObjectIDPairVectorInsertOverflowBody.cpp supplies byte-matched control flow, but its enum label is not evidence of the record identity.

The two pins name template instantiations over the address-qualified record and pin the independently decoded body addresses; the resolver discovers their ILT entry points. The callback body was compared against the canonical retail image; the normal scoped gate passes all 308 bytes and both string literals after resolving all 19 relocations.
