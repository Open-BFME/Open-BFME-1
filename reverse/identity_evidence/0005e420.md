# CategoryModuleTemplate<8> array cleanup at 0x0005E420

The 84-byte retail wrapper passes element size 12 and destructor ILT 0x000259EB
as the callback to the array-destruction helper at 0x009F6D76. Its scalar arm
calls the same ILT directly. The ILT jumps to 0x0005E370, whose complete 33-byte
body installs the two CategoryModuleTemplate<8> base vtables at +0 and +4.
The existing matched CategoryModuleTemplate<8> scalar-deleting destructor at
0x0005E3F0 independently calls that same ILT. The matched constructor at
0x0005E340 installs the corresponding vtables and sets bytes +8/+9, consistent
with the wrapper's 12-byte element size. These establish the destructor family
independently of this replacement's byte shape.

Five HashTemplateClass<StringClass, ...>::Entry vector-deleting claims shared
this range. The full gate rejects all five at the scalar destructor call: their
0x00013101 candidate reaches 0x005D5760, not 0x0005E370. That is a different
FXParticleSystem template destructor. Adding 0x000259EB as a HashTemplate pin
would conceal the incorrect identity. This change retires the five claims and
replaces them with one compiler-generated C++ array destructor for the proven
CategoryModuleTemplate<8> family. No inline assembly or emitted instruction bytes
are used. Each removed identity has a tombstone against union-merge resurrection.

The original 84-byte range is preserved exactly, with no new byte coverage.
Probe: 84/84 bytes, five relocation sites, exact outside relocations. The scoped
build must also validate every relocation before this is committed. The five
corresponding known-red baseline rows are removed in the same change.
