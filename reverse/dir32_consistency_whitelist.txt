# Global singleton pointers / file-scope statics materialized at multiple retail
# addresses. FiringTracker.cpp's newly-matched getModuleNameKey/getClassMemoryPool
# references several of these; each reference is from a byte-matched function.
#
# ?TheControlBar@@ is NOT one of those, and its entry here is masking a real
# discrepancy rather than recording a legitimate one. Five matched rows bind it to
# 0x012F33F8 (ControlBarObserverSystem, GeneralsExpPointsSystem); exactly one,
# commandButtonTooltip in ControlBar.cpp, binds it to 0x012ED7AC. That address is
# provably TheScienceStore: ScienceStore::friend_parseScienceDefinition is what
# the INI block table registers for the "Science" keyword, it byte-matches, and it
# reads 0x012ED7AC as a store with the m_sciences vector at +0x08/+0x0c.
#
# So retail's commandButtonTooltip loads the science store, not the control bar,
# and our source's TheControlBar->showBuildTooltipLayout(window) reproduces the
# bytes only because the DIR32 slot is masked and the call happens to land on the
# same vtable index. The name is wrong even though the row matches -- exactly the
# failure this check exists to catch. Left whitelisted so the gate stays green,
# but it should be resolved by working out what BFME's commandButtonTooltip really
# calls, not by treating two bases as expected.
#
# A third caller has since turned up, and it points the same way. The INI block
# registry binds the "PlayerAIType" keyword to 0x000DF1A0, whose whole body is
#   mov ecx,[0x12ed740] ; push ini ; call 0x0003EBD5
# and 0x12ed740 is ThePlayerAITypeSet -- named by the string literal
# GameEngine::init pushes immediately before it (tools/dump_subsystems.py). That
# same thunk 0x0003EBD5 is what reverse/symbols.csv records twice, once as
# ?friend_lookupScience@ScienceStore@@ and once as
# ?showBuildTooltipLayout@ControlBar@@, both "pinharvest x1".
#
# So three call sites with three different `this` globals reach one address, and
# the function there (0x000DEEC0, 578 bytes) does a lookup over a vector of
# 16-byte elements at this+0x08 and appends when the lookup returns -1. That is
# not the shape of showBuildTooltipLayout, and ScienceInfo is 0x30 bytes rather
# than 16, so it is not friend_lookupScience over m_sciences either.
#
# The PlayerAIType binding is the strongest of the three, because the registry is
# ground truth for what a keyword does: the block table itself says this function
# parses a PlayerAIType entry. The other two look like harvest guesses that were
# never contradicted, since the addresses they resolve are masked. Nothing is
# renamed on that basis alone -- it is recorded so the next person starts from
# three data points instead of one.
#
# RESOLVED, in the sense that the mechanism is now understood even though the
# rows are left alone. Retail's function at 0x000B8F40 is seventeen bytes:
#
#   mov eax,[esp+4] ; mov ecx,[0x12ed7ac] ; push eax ; call 0x17503 ; ret
#
# 0x12ed7ac is TheScienceStore, and 0x00017503 is a five-byte incremental-link
# thunk whose real body is 0x000E7240 -- the 85-byte function functions.csv
# already matches as ?friend_lookupScience@ScienceStore@@. So retail loads the
# science store and calls a science-store method, exactly as this note suspected.
#
# What kept it invisible is a second bad row rather than a subtle one:
# ?showBuildTooltipLayout@ControlBar@@QAEXPAVGameWindow@@@Z is recorded at
# 0x00017503 with size 5 -- that is, it claims the ILT thunk itself, not a
# function. A five-byte jump matches trivially, so our ControlBar.cpp source can
# call TheControlBar->showBuildTooltipLayout(window), have the REL32 resolve
# through that thunk row, and byte-verify while naming both the global and the
# callee wrongly.
#
