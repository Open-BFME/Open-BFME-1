## Ruled out this session

1. **`__declspec(dllimport)` spelling of the formatter.** It emits `FF 25 [__imp_...]`, 6 bytes,
   where retail has one `E8` REL32, 7 bytes inside a 75B extent whose next byte belongs to the
   following section. The extent cannot absorb the indirection, so dllimport is not a route to a
   byte match for this body. (Existing precedent `game/Libraries/Source/string/StringBaseFormatForwarders.cpp`
   uses dllimport only because *its* retail body is a `FF 25` forwarder.)
2. **Calling the gen-import glue name directly.** `?ji_009f719c@@YAXXZ` carries an int/no-arg
   signature, so a correctly-typed call from my TU mangles to a different symbol; a matching
   symbol would be a no-arg call, which is not retail's four-word cdecl call. Ruled out by the
   spelling at imports_000.cpp:327.
3. **Making the `route=` pin admissible by re-wording the note.** `tools/pin_consistency.py`
   `route_verdict` (lines 339-377) requires *both* arms: the PE import directory must name the
   pin symbol (`undecorated_forms(name)` must contain `MSVCR71.dll`'s export
   `?vswprintf@@YAHPAGIPBGPAD@Z`) **and** the ledger's matched gen-import row at 0x009F719C must
   carry `target=` in the same spelling set. Reproduced refusal for the decorated name:
   `0x009F719C: the ledger's gen-import row targets vswprintf, not ?vswprintf@@YAHPAGIPBGPAD@Z`;
   for the bare `vswprintf` name it fails the first arm instead. So no admissible spelling exists
   today, and the rule is not mine to widen ("do not widen the rule").
4. **Repairing the stale `target=` note through a sanctioned writer.** The row is generated glue:
   `game/gen_small/imports_000.cpp` says "Generated by: python3 tools/gen_small.py gen-imports
   --batch 0 --limit 500 / Do not edit by hand; regenerate instead", and `tools/gen_small.py`
   does not exist in BFME 1 (`git ls-files tools | rg gen_small` -> none).
   `tools/import_binding.py` writes only `__imp_` pins (`pin`, `retire-pin`); `ilt_repair.py`
   applies ILT-oracle renames (`--kind pin|tu-access`). Neither writes a `gen-import` `target=`.
   `add_match.py --replace-archive-import` only promotes a gen-import row into a vendored
   archive's dispatch thunk, not a target-note repair.
