## New, untested leads for an agent with Wine

1. The 564 B regressions from memset may have hidden the effect on order. Every memset
   trial that regressed to 564 B was also the old register-allocation state (the 0.80 bank
   was 564 B with slot=ESI and zero=EBX). Shape_levers row 224 says the memset intrinsic
   puts the destination last, which is retail's [8] order. Try a memset for **only** the
   [8] clear, keep the first two as the loop `reset()`, and keep the bank's FrameDataManager
   local and nested if. Then check whether the 564 B comes from allocation (diff the whole
   body, not just +0x19A). If allocation moves, add the allocation lever again.
2. Retail emits `eax, ecx, edi` for the constant case. That is neither pure loop order
   (edi, ecx, eax per row 224) nor pure memset order (ecx, eax, edi). It may be the
   memset intrinsic with eax already scheduled first because `eax` (m_localSlot) dies at
   the compare. Try `memset(&m_commandHistory[8], 0, sizeof(BFMECommandIDHistory))` with
   the compare operands swapped (`m_packetRouterSlot != m_localSlot`). The compare bytes
   (+0x18A..+0x196) must stay `mov eax,[ebp+0x12028]; cmp eax,[ebp+0x1202c]`.
3. ZH is not useful here: ZH has no command-ID histories. The BFME 2 donor calls an
   out-of-line clear (0x004D04C9), so neither reference has an inline form.
