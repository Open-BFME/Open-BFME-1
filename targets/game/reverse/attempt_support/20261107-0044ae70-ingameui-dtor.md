# InGameUI::~InGameUI (0x0044AE70, 936 B): EXACT via inline STLport member destructors

Target `??1InGameUI@@UAE@XZ`, RVA 0x0044AE70, 936 bytes. Starting bank
`targets/game/reverse/attempts/0x0044ae70.cpp` (2026-10-20, 0.969) reproduced as
logged: 936/936 B, 64 relocs, shape 1.000, 29 non-reloc diffs. The only residue was a
register swap. Retail keeps zero in EBX and `&m_currentlyPlayingMovie` (this+0x14) in
EBP; the bank had them the other way round.

Best candidate: `build/wf/0044ae70/best.cpp`. probe: `result EXACT (modulo relocation
slots)`, 936/936, 64 relocs. Flags are the bank's own (`/DNDEBUG /MD /EHsc
/D_STLP_USE_STATIC_LIB /D_STLP_NO_EXCEPTIONS`, WWLib + Common/System includes) plus the
`// stlport` marker, as in the sibling `InGameUIConstructor.cpp`. Compiler flags are
unchanged.

## Fix

The bank declared each member destructor out of line. Retail's body and its unwind
funclets call *different* functions for the same members:

| member | body calls | funclet calls |
|---|---|---|
| +0x10 | 0x440400 (`_List_base` dtor, 66 B) | 0x4427C0 (`list` dtor, 5 B) |
| +0x18/+0x1C | 0xFD1D0 | j_48DD3 → 0x4FD750 |
| +0x77C | 0x4491D0 (`_Rb_tree` dtor, 124 B) | 0x449870 (`map` dtor) |
| +0x1298, +0x12C0, +0x12C4, +0x1304 | 0x4400F0, 0x4401E0, 0x4402D0, 0x440510 | four other thunks |

So those members have inline container destructors that wrap an out-of-line base
destructor. The fix uses the constructor TU's own STLport types for the eight members:
`list<WindowLayout*>`, `list<Drawable*>` ×2, `map<AsciiString,void*>` (12 B, so the
following pad is `[7]`), `list<void*>` ×3 and `list<Payload0044B800_1304>`. With that
change MSVC 7.1 puts the zero in EBX and the movie address in EBP.

Equivalent opaque form, also EXACT (`w1.cpp`/`w3.cpp`): `template<int N> struct
Inner { ~Inner(); }; template<int N> struct Wrap : Inner<N> { ~Wrap() {} };` on the same
eight members.

## Measured mechanism (diagnostics, not landed)

- The zero register takes EBX only when the zero web has a byte use. Two diagnostics
  show this:
  - A byte compare (d2) flips it.
  - An out-of-line `~Snapshot` (sg) flips it, because it emits the EH state-0 store
    `mov byte [esp+0x20], bl`. Adding `throw()` to that out-of-line dtor (sq) drops the
    store, and the swap returns.
- Removing the Snapshot base also flips it (g1). That case has a state-0 byte store too,
  and it matches the old 917-byte banks, which had EBX.
- Wrapping only some members is not enough. Tested subsets, all still 29 diffs:
  - +0x10
  - +0x18/+0x1C
  - +0x77C
  - +0x12xx
  - +0x1304
  - +0x10/+0x18/+0x1C/+0x77C
- Hypothesis, not proven: the inline wrapper expansions keep a dead state-0 store alive
  until register allocation, and a later pass removes it.

## Shape lever (candidate entry for docs/shape_levers.md)

- Symptom: zero is in EBP and an address CSE is in EBX; retail has the reverse. The
  function has an EH destructor with a secondary base whose inline dtor only resets the
  vptr.
- Fix: give members whose retail body-call target differs from their funclet target an
  inline wrapper destructor. Use the real STLport container types.
- Measured effect: the zero web takes EBX, the register that byte stores need. Source:
  `build/wf/0044ae70/best.cpp`.

- The InGameUI members are the constructor TU's STLport types (`list<WindowLayout*>`, `map<AsciiString,void*>`, ...).
- The ledger rows at those addresses carry guessed `list<int>` / `Gen_*` instantiation names.

Landing therefore needs one of two things:
- **Option (a):** a class-level reconciliation that re-homes those `tg_` rows to the evidenced instantiation names. The evidence is the InGameUI constructor TU's member types plus this destructor's call sites.
- **Option (b):** declaring opaque base destructors under the existing object-symbol names. That works only where the names are unique: five addresses share the same list<int> symbol, so they cannot be told apart this way.
