# 0x0005F270 is StringBase&lt;char&gt;::str; retire the AsciiString/UnicodeString over-claims

Three `matched` rows claim the same 16 bytes at 0x0005F270:

- `?str@?$StringBase@D@@QBEPBDXZ` (game/Libraries/Source/string/StringBase.cpp)
- `?str@AsciiString@@QBEPBDXZ` (game/.../fx_particle_system_module_keys.cpp)
- `?str@UnicodeString@@QBEPBGXZ` (game/.../W3DDevice/GameClient/W3DDisplayString.cpp)

Retail was linked without identical-COMDAT folding, so only one of them is real.

## Decisive evidence

1. The body at 0x0005F270 falls back to the *narrow* empty string:
   `mov eax, 0x0107388B` (`?Rva006A16B0Empty@@3PADA`, verified in the unpacked
   1.03 image). A `UnicodeString::str` body must return the wide empty
   (0x0107388C), so row 3 is ruled out by its own return value.
2. Exactly one jump targets 0x0005F270: the 5-byte thunk at 0x00037F3D.
   `exports.csv` names that thunk `?str@?$StringBase@D@@QBEPBDXZ`, and the row
   for it carries the matching `export_rva` (0x00037F3D -> 0x0005F270).
3. The null's own export (`?TheNullChr@?1??str@?$StringBase@D@@QBEPBDXZ@4DB`)
   scopes the static inside `StringBase<D>::str`, not inside either forwarder.
4. The image holds exactly two str-shaped bodies: narrow at 0x0005F270 and
   wide at 0x0005F290 (owned by `?str@?$StringBase@G@@QBEPBGXZ`, thunk
   0x0002287C). There is no third body for a separate AsciiString or
   UnicodeString out-of-line copy; both forwarders inline at every retail
   call site (`one_identity --callers`: no C++ caller names any row here).
5. Between the two narrow spellings, the linker-known name (export + thunk)
   is the template definition. `AsciiString::str` is a pure header forward
   with no out-of-line body anywhere in retail.

## Action

Retire rows 2 and 3 to `deleted_rows.csv`; keep row 1. Drop the three
`one_identity.surplus` lines for 0x0005F270 (surplus 2084 -> 2082) and prune
the two stale `ilt_contradicted_baseline.txt` keys. No source changes: both
owning TUs keep verifying on their remaining rows.
