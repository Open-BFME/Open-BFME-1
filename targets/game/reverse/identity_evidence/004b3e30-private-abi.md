# Rva004B3E30 private ABI

The target retains an address-derived identity. Its original source-level name is not established. Its observable operation toggles the combo-box list and resizes the owning window. The reconstruction uses the canonical `GameWindow`, `WinInstanceData` and `GameWindowManager` declarations and an address-derived view of BFME's list data.

## New experiment

Earlier attempts identified an incoming EBX window pointer but did not compile a complete reconstruction. The retry hypothesis was that the complete decoded caller at RVA 0x004B4010 would let MSVC 7.1 reproduce this compiler-private convention. A helper emission that still read a stack argument or ECX, or a caller that marshalled a different window value, would refute it. The ordinary cdecl trial had a stack argument. The static helper compiled beside the real caller reads incoming EBX, and the caller preserves its first argument in EBX across the audio calls before calling the helper without stack arguments.

## Boundaries and callers

The target extent is 384 bytes at RVA 0x004B3E30. Its two return instructions are at RVA 0x004B3F91 and RVA 0x004B3FAF. The latter is immediately followed by INT3 padding. All conditional branches and internal jumps stay inside this extent. The early null branch reaches the shared stack cleanup at RVA 0x004B3FAC. There are no tail jumps, stack parameters, hidden result storage or exception states in this helper. The indirect calls use the two manager virtual slots described below. Its result is unused by both callers.

The complete decoded callers are RVA 0x004B4010 and the existing `GadgetComboBoxSystem` body at RVA 0x004B42F0. The former loads its first cdecl argument into EBX at RVA 0x004B4029 and calls the target at RVA 0x004B4179 without marshalling another argument. The latter copies its window from ESI to EBX at RVA 0x004B4738 and calls the target at RVA 0x004B473A. The target does not overwrite EBX. The reconstructed caller context remains marked `present-unmatched`; this assignment does not change its existing ledger ownership or claim its conversion. Its executable instructions end after RET at RVA 0x004B422A. Its switch tables occupy the following bytes through RVA 0x004B4254. The retained context matches both the executable instructions and those tables.

## Fields and call contracts

The target calls the actual `winGetUserData` body at RVA 0x00478C70 through ILT RVA 0x00046538. That complete four-byte body returns the dword at receiver offset 0x2C. The combo data is obtained twice. Retail writes a byte at combo offset 0x1C, reads the list pointer at 0x2C, compares the signed entry count at 0x20 with one, and later compares it with the signed maximum at 0x04. The landed `GadgetComboBoxGetLength` and combo accessor sources corroborate these fields. The ZH left-up branch supplies the resizing control flow but does not supply BFME's added list fields.

The list view reads child-window pointers at 0x1C, 0x20 and 0x24. It writes separate one-byte flags at 0x12 and 0x13 and copies the four-byte selected position at 0x34 into the unknown four-byte field at 0x30. The flags and destination retain opaque names. The complete target witnesses every access used by this view; the landed `GadgetListBoxInput.cpp` independently carries the same BFME offsets. A typed list declaration lets the compiler schedule the 0x34 load before the independent flag stores, as retail does. An explicit scalar temporary instead changes later scheduling and does not match.

Each direct call was decoded through its ILT and checked against the complete final body. `winHide(bool)` consumes a byte-valued argument in a four-byte stack slot and returns with RET 4. `winGetSize(int*, int*)`, `winSetSize(int, int)` and `winSetPosition(int, int)` return with RET 8; the caller pushes the height or second pointer before the width or first pointer. The instance-data getter returns receiver plus 0x30. The font read is at instance offset 0x184, which the layout witness identifies as `m_font`. `winIsHidden()` produces its Boolean in AL. The existing `HideListBox(GameWindow*)` consumes a cdecl window argument; retail performs the four-byte caller cleanup after that call.

The manager singleton uses its already recorded `TheWindowManager` symbol. Its primary vtable at VA 0x010F8B60 routes slot 47 (+0xBC) through ILT RVA 0x000033C3 to `winSetLoneWindow` at RVA 0x0047D040, and slot 67 (+0x10C) through ILT RVA 0x00043748 to `winFontHeight` at RVA 0x0047A060. The former consumes one window pointer and returns with RET 4. The latter consumes one font pointer, reads the signed height at font offset 0x10, and returns with RET 4. The caller context's slot 48 (+0xC0) routes through ILT RVA 0x00045D4A to the four-byte getter at RVA 0x0047D080, which returns manager offset 0x28 without stack cleanup. Its source uses a typed member-pointer dispatch and does not assert an unproved method name.

## Caller exception cleanup

The caller constructs its audio object through ILT RVA 0x00025306, which reaches the complete constructor at RVA 0x000B2CC0. That constructor receives an AsciiString reference and an integer, initializes the vptr and fields through offset 0x6C, and stores the second argument at offset 0x28. The complete `commonInit` body at RVA 0x000B24C0 was also decoded; all of its writes and string cleanup stay within this object, including the final dword at 0x68. The constructed object spans 0x70 bytes. The caller's opaque audio declaration supplies that storage and a virtual destructor, without claiming the original class identity or exposing guessed members. `audio_type_helpers.disasm.txt` also retains the full counted-pointer destructor and the narrow string constructor and release helper used by this context.

The caller's retail FuncInfo has three states: state 0 to -1 destroys the temporary string at EBP minus 0x80; state 1 to 0 destroys the audio object at EBP minus 0x7C and then the string; state 2 to -1 destroys only that audio object. The compiled context has the same predecessors, receiver adjustments and cleanup calls. The audio cleanup reaches ILT RVA 0x00026F35 and the complete destructor at RVA 0x000B31F0. The constructor and destructor unwind maps were followed: string cleanup uses offsets 0x04, 0x14, 0x18, 0x1C and 0x6C; counted metadata at 0x08 is released through its refcount decrement and flag-one virtual destructor. The target helper itself owns no objects and has no unwind map.
