# ShaderClass::Apply at RVA 0x00911020

## Result and refutation

The Open BFME 2 donor `Code/Libraries/Source/WWVegas/WW3D2/ShaderClassApply.cpp` at game.dat RVA 0x00137590 supplies the missing source structure for the alpha-test policy. The saved BFME 1 reconstruction has 16 non-relocation differences between +0x6A and +0x14E. Separating mode 2 from the two complementary source/destination blend tests, then applying the enabled alpha state in one shared block, removes those differences. Both the complete scratch trial and the port into the existing `game/Libraries/Source/WWVegas/WW3D2/shader.cpp` reproduce the 2915 executable bytes and the following 93 bytes of alignment and switch data. This result would be refuted by any difference in the strict resolved body, a relocated call to a different callee, or a switch-table destination that differs from retail. The donor is a same-name near twin, not independent BFME 1 identity evidence.

## Identity and ABI

The complete 774-byte matched caller `DX8Wrapper::Apply_Render_State_Changes` at RVA 0x00904890 loads ECX with the shader member at VA 0x01340EC0 and directly calls the target at caller +0x16. Its authored source names that call `render_state.shader.Apply()`. The canonical `shader.h` declares private `void ShaderClass::Apply()` and a four-byte `ShaderBits` member at offset zero. The target saves ECX as its receiver, reads that member, takes no stack arguments and uses no hidden return storage. The existing Apply pin cites this caller and the official WW3D implementation. The proposed identity would be refuted if the call's receiver were a different subobject or the target required an argument or returned a meaningful value absent from the caller.

All 15 render-state calls reach ILT RVA 0x0001321E, whose complete five-byte jump reaches the existing 193-byte `DX8Wrapper::Set_DX8_Render_State` body at RVA 0x006C5740. All 24 texture-stage calls reach ILT RVA 0x000261E3 and its existing 255-byte body at RVA 0x006C5840. Complete decoding of both setters confirms their argument reads and all return paths. The render-state setter reads two four-byte stack arguments in state/value order, returns with plain RET and forwards the device receiver and both arguments through vtable offset +0xE4. The texture-stage setter reads stage/state/value as three four-byte stack arguments, returns with plain RET on both paths and forwards them through +0x10C. Apply supplies those arguments in reverse push order and performs the corresponding cdecl stack cleanup. Existing pins resolve consistently through both thunks; no pin was added.

The direct device calls inside Apply load the device from VA 0x01340534. The +0x10C calls push value, state, stage and the same device receiver. The +0x104 calls push a null texture pointer, stage and receiver. The +0x13C call supplies one four-byte float and receiver. Their argument slots are removed by the called stdcall methods; subsequent stack accesses use the restored stack position. HRESULT results are unused. TU-local static force-inline adapters retain these measured slots because the SDK D3D8 interface supplied by the common shim has a different slot order. They emit no additional out-of-line body. Apply has no exception frame, constructor cleanup or ownership transfer.
