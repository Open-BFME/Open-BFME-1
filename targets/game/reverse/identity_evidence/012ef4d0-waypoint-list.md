# Waypoint list head at VA 0x012EF4D0

The datum is one four-byte `Waypoint *`, initially null in the virtual zero-filled tail of retail `.data`. There are no initial relocations, and the unpacked PE has no base-relocation directory. No data row overlaps its range, and no other DIR32 address lies inside it. TerrainLogic's static water handle begins at the next address, 0x012EF4D4. The chosen existing spelling is `?g_waypointListHead@@3PAVWaypoint@@A`.

The independently matched Waypoint constructors at RVAs 0x001AB600 and 0x001AB8B0 store the prior global head at receiver +0x1C, link the previous head back to the receiver, and publish the receiver itself at 0x012EF4D0. The matched Waypoint destructor at RVA 0x001ABA80 updates the same head from the next node when removing the first node. Named TerrainLogic methods getWaypointByName, getWaypointByPath, getClosestWaypointOnPath, getWaypointByID, newMap and xferTerrainState read this chain. The drain at RVA 0x001A2D50 and reset at RVA 0x001ACF90 repeatedly invoke the node's deleting destructor until the head is null. Node +4 is the waypoint ID and +0x1C is the next link. These are independently compatible with the Zero Hour Waypoint declaration and named TerrainLogic lookup operations, although BFME stores the head globally rather than in the reference TerrainLogic object.

Before correction, four game sources declare `g_waypointListHead` as `Waypoint *`; two declare `g_rva012EF4D0` as an address-derived node pointer; one declares `g_Va012EF4D0` as `HeapNode *`; one declares `g_Va012EF4D0` as `int`. The list's identity is supported by the constructors and lookup consumers rather than by those counts. All declarations now use the established Waypoint spelling. Partial layout views are reached through explicit casts, and the two six-byte getters retain their existing integer return ABI through a pointer-to-integer cast. No function signature or identity is changed.

Raw evidence is `build/rlink/012ef4d0-retail.log` (bytes, bounds, all direct references and declarations) and `build/rlink/012ef4d0-bodies.log` (complete retail bodies and each direct call route). The datum is defined once in WaypointConstructor.cpp beside the constructors which publish it. The additive data gate proves its four-byte allocation and zero initial bytes. A constructor that publishes a different receiver identity, a node layout inconsistent with the named Waypoint consumers, a store that treats this cell as an integer count, or an overlapping datum would refute the correction. The semantic names of the address-derived getter bodies remain outside this datum correction.
