## Boundary and ABI evidence

The complete retail extent is `[0x002C3E00, 0x002C3F7E)`. It ends in `ret 12` at `0x002C3F7B`; every conditional branch and the one internal jump reach instructions within that extent. The complete caller at `0x002C3B90` zero-extends its owner's byte at `+0x24`, pushes that value, the address of a one-byte local, and the address of a twelve-byte local. It passes its unchanged owner in ECX. Its call at `+0x95` reaches ILT `0x00033A87`, whose complete five-byte body jumps to the target. The caller subsequently reads the three coordinate fields and the boolean byte. Together with the target's three argument accesses and `ret 12`, this supports the bank's `void __thiscall(Coord3D *, bool *, bool)` declaration. There is no hidden return storage or receiver adjustment. EAX holding the output pointer in the epilogue is incidental; the caller does not consume a return value.

The target's call at `+0xF5` reaches ILT `0x0002A991`, whose decoded jump reaches `0x002C3FE0`. The complete landed helper at that address reads the first argument's `+0` and `+4` fields as float arguments to the terrain virtual call, compares a floating-point result against its second stack argument, returns false or true in AL, and uses a common `ret 8` epilogue. The target pushes the candidate address after the computed float height and tests AL. Its unchanged owner is the receiver. This independently confirms the existing helper's argument order, widths and return width. Its indirect terrain call at `+0x39` pushes normal pointer zero, coordinate Y, then coordinate X and consumes ST(0) as a float; this agrees with the existing helper declaration. No new callee identity or pin is proposed.

The owner chain is `this+0x1C -> +0x10`. Retail reads the object's position at `+0x38`, `+0x3C`, `+0x40`, its matrix axis at `+8`, `+0x18`, `+0x28`, and its locomotor pointer at `+0x204`. The locomotor's `+4` pointer supplies float fields `+0x74`, `+0x78`, `+0x7C`. These are layout and access-shape claims, not semantic member names. The existing bank's address-derived views remain unchanged. The native Matrix3D and Vector3 headers implement precisely these three axis fields and the scalar multiplication used here. The registered canonical Coord3D header agrees on three floats and twelve-byte size but lacks the inline coordinate operations; the existing bank's native `Lib/BaseType.h` supplies those operations without introducing a private Coord3D declaration. There is no shared header for `Rva002C3FE0Owner` in this revision. `name_oracle` reports no witnessed owner layout. The Zero Hour AIUpdate search supplies no independently named twin for this operation.

The four bytes at retail VA `0x0107533C` decode as float `0.5`. The target has no exception handler, ownership cleanup, container or value-construction helper. Constructor unwind and container payload checks therefore do not apply to this target. The landed helper's internal exception machinery is not changed or claimed as a new recovery.

## Hypothesis and measurements

The earlier missing-callee blocker is resolved by the existing typed, landed helper. The new hypothesis was that a native vector object omitted by the earlier source caused the twelve-byte frame deficit. Refutation would be an unchanged frame and displacement pattern after adding an actual used native object, or an improvement that disappeared when the saved body was reprobed at the retail extent.

The old bank reproduces its measured 382-byte body with 40 differing non-relocation bytes. A native Vector3 position followed by a Coord3D copy reproduces the retail frame and lowers the differences to 26. Declaring the candidate at function scope puts the two coordinate records in retail's order but adds a four-byte compiler temporary. Replacing the three-argument coordinate setter with scalar field copies removes that temporary and lowers the differences to 14. The final bank candidate remains 382 bytes with two aligned, independently resolved relocations and no unresolved symbol. The quality is computed from the matching-byte fraction, `368/382`, rather than estimated. The old and final raw probes are `original-bank-probe.log` and `bank-candidate-probe.log` in the task directory. The raw candidate byte gate is `scoped-gate.log`; it fails on the same residue and is not a passing recovery.

The fourteen relocation-resolved differing byte offsets are `+0x060`, `+0x094`, `+0x096`, `+0x097`, `+0x09B`, `+0x09D`, `+0x09E`, `+0x0A2`, `+0x0A6`, `+0x0AA`, `+0x0AE`, `+0x0B2`, `+0x0CE` and `+0x0DC`. Their exact retail and candidate values are retained in `build/rva002c3e00/resolved-differences.json`. The first remaining difference stores direction Z at `esp+0x3C` instead of retail's `esp+0x48`. The other differences reverse the X/Y multiply load operands, swap the position Y/Z load order, and use the native position's slots for intermediate Y/Z copies where retail uses the candidate's slots. Frame allocation, coordinate output slots, call offset and the remainder of the instruction stream agree.

## Rejected shapes and reopening condition

Every numbered trial source, compiler listing and unedited probe log is retained under `build/rva002c3e00/`. Native return assignment, output-axis access, reference binding, coordinate setters and widened local scopes do not repair the original frame. A vector-view aggregate copy reaches the desired frame but emits extra instructions. A coordinate-return helper produces an even larger frame. Using a native Vector3 candidate gives a shorter, less similar body. Adding the actual used native position object is the successful frame lever; copying it through the setter leaves an additional scalar temporary, while scalar copies remove that temporary. The positional-copy scope and native-copy variations are recorded separately and are not equivalent to an exact result.

The supplied shape-family generator produces two choices. The bounded search tries the unchanged best body, the achieved/last store-order swap, and the limit/step declaration swap. The store-order change worsens the byte count, and the declaration swap does not improve it. Sources and raw probes are `family-000.cpp` through `family-002.cpp` and their probe logs. The unedited search manifest is `build/shape_search/00e34955dadf45e1a31345848e9b9f8c/result.json`; `family-search.log` retains its output. A reused native position object obtains retail's direction-Z slot but changes the initialization instruction stream and loses the better body. Its assignment and output-axis alternatives do not change that result.

Reopen with independently justified source or inline-helper context that preserves direction Z in `esp+0x48` while writing the position Y/Z copies directly to the candidate slots and reproducing the observed multiply load order. Repeating the recorded assignment, scope, setter, native-copy or declaration-order experiments supplies no new evidence. The remaining blocker is stack-slot and float load allocation. No semantic identity is claimed, no new source recovery is landed, and no ledger row or pin is changed.
