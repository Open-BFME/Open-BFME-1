# RVA 0x007897D0 destructor

Retail is 184 bytes through `ret` at `+0xB7`, followed by INT3 at `+0xB8`.
All addresses below were independently checked in the unpacked BFME1 1.03
retail image with Capstone and pefile.

The existing matched constructor `Rva00789900Init::Rva00789900Init` at
`0x00789900` installs vtable VA `0x01126CCC`. The destructor installs that
same table. Its slot zero stores ILT VA `0x0041C756`, routing to the scalar
deleting wrapper at `0x00789950`. That wrapper calls this destructor through
ILT `0x00047EF1`, conditionally deletes its receiver for flag bit zero, and
returns the receiver with `ret 4`. The existing address-derived owner is
therefore reused. No canonical EA class or method name is claimed.

## Lifetime evidence

The body explicitly releases fields `+0x10`, `+0x0C`, and `+0x18`, using a
signed dword reference count at referent `+4`, virtual slot zero on reaching
zero, and a conditional null store back to each field.

`eh_info.py 0x007897D0` reports three states:

- State 0 -> -1 calls `0x00789740` on the saved receiver through ILT
  `0x00038FFF`. Its complete 67-byte body releases the string at `+8`, then
  restores vtable VA `0x010F6F58`. It has **no entry vtable store**. It is
  independently matched in `BigTwoMemberDtors.cpp` as `Rva00789740`.
- State 1 -> 0 calls `0x00789600` on receiver `+0x20` through ILT
  `0x0003D109`. Its complete 49-byte body releases and conditionally nulls
  the two adjacent reference pointers at subobject `+0/+4`. The existing
  address-derived ledger alias already emits this exact two-reference
  cleanup from `W3DShadowHelperManagerDtor.cpp`; no new semantic identity is
  inferred from that alias.
- State 2 -> -1 calls `0x0045DD10` on the receiver through ILT `0x00005169`.
  Its complete seven-byte body only stores vtable VA `0x010F6F58` and returns.
  The existing binding names this table `VirtualMinusOneConstructorThunk`.

Those cleanup routes explain the inline state transition before the `+0x20`
release pair and the later state 2 before the string release. The old bank
instead put the string directly in the outer class and manually released
all five pointers, losing the intermediate lifetime boundary.

The reconstruction models the zero-offset cleanup subobject using a
`__declspec(novtable)` base view, whose string and sentinel cleanups match
`0x00789740`. The attribute represents the independently observed absence
of its entry vtable store. The actual EA source hierarchy (base versus a
zero-offset composition) is not recovered or asserted. A plain composition
probe produced the same 184-byte extent and cleanup sequence but scheduled
its explicit outer-table assignment after the first field load; the native
outer destructor plus this base view reproduces the observed store order.

The two-reference member at `+0x20` has its own ordinary C++ destructor.
The real `AsciiString` header supplies the string lifetime and canonical
`StringBase<char>::releaseBuffer` call. No assembly, volatile fields, new
pins, shared-header edits, or generated-source edits are needed.

`name_oracle.py` reports no witnessed layout for `Rva00789900Init`,
`Rva00789740View`, or `Rva00789600Pair`. Strict source verification matches
all 184 bytes and both vtable DIR32 references.

## Bank-removal naming pairs

The checker pairs old `BaseSentinel007897D0` with the new
`Rva00789740View`, but the old sentinel actually corresponds to the reused
`VirtualMinusOneConstructorThunk` binding. The new view additionally models
the independently decoded string lifetime. This is a false pairing, not a
rename. The outer `Owner007897D0` becomes the already-established
`Rva00789900Init` constructor owner on the independent vtable evidence
above; both are address-derived names. Exact snapshot corrections record
these two checker findings without exemptions for future edits.
