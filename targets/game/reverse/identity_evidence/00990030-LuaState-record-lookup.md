# Lua state parameter identity at RVA 0x00990030

The 52-byte matched body in `game/GameEngine/Source/Common/Rva00990030RecordLookup.cpp` takes a `lua_State *` and a signed index and returns an unsigned value. `targets/game/reverse/symbols.csv` pins `?Rva00990030Lookup@@YAIPAUlua_State@@H@Z` to RVA 0x00990030 with a reviewed state-layout and cdecl-argument note. The retired spelling `?Rva00990030Lookup@@YAIPAURva00990030Range@@H@Z` describes the same body with an opaque type that prevents the Lua callers from linking.

Retail reads the index from `[esp+8]` and the state from `[esp+4]`. A nonnegative index selects `base + index - 1` using the pointer at state offset 0x10 and 16-byte slots, rejecting a slot at or above `top` at offset 0. A negative index selects `top + index`. The body accepts only a nonnull slot with tag 4, follows its pointer at offset 8, and returns the unsigned word at that object's offset 0x0C. `game/Libraries/Source/Lua/lstate.h` declares `top` as the first state field and `Cbase` after three further 32-bit fields. `lapi.c` uses these fields with the same positive and negative index rules. The local ABI slice names the offset 0x10 field `base`; the record and extracted-value types retain their address-derived names.

The matched retail caller `ObjectEnterUncontrollableCowerState` at RVA 0x002E6420 passes the same state pointer to this body at call sites 0x002E6429 and 0x002E644B and to `lua_type` at 0x002E643A and 0x002E645C. The matched `ObjectPlaySound` caller at RVA 0x002E6850 passes its state to `lua_gettop` at 0x002E6871, this body at 0x002E6893, and `lua_type` at 0x002E68A4. These are direct calls to RVA 0x00990030; no thunk, alias, forwarder, or replacement accessor is needed.

The correction changes the provider's parameter type to the pinned spelling and respells the eight callers using the old type. It preserves the provider's 52-byte extent, field offsets, record stride, return contract, and instructions. A caller supplying a different object than its Lua API state, a retail target other than 0x00990030, a different field offset or slot stride, or any changed instruction byte would refute the correction.
