## New hypotheses and observations

The saved body appended a remainder after reaching the item limit and entered string construction for a negative argument count. Complete target decoding shows that reaching the limit skips remainder creation and that a negative count returns the newly allocated array without constructing strings. Correcting those paths produced the native `sub esp,0x18`, which the saved body lacked. The target's final remainder assignment calls the complete out-of-line helper at `0x008A9A70`; the saved body had inlined that assignment. The hypothesis would be refuted by either a decoded branch reaching remainder construction on the limit path or an out-of-line assignment call on the delimiter-found path. Neither occurs.

The allocator header was modeled as two DWORDs, following the landed `Rva008A7270.cpp` source and the independently decoded cleanup at `0x008A9120`. The native allocator sequence forms `storage = raw + 2`, registers that pointer and constructs a 44-byte object. The cleanup unregisters the object and frees `storage-8` with `size+8`. This representation produces retail's `lea esi,[eax+8]`; the byte-pointer and integer-address spellings produced a different sequence. An actual cleanup using the unadjusted allocation address or another object size would refute this ownership model.

The index is initialized after copying the input string, rather than at function entry. This restores the delayed EBX and EBP save region. A conditional offset view of the value's string improves the masked byte distance over a branched typed-member accessor. Restoring the shared separator-length local worsens that distance. The best candidate retains the older bank's descriptive `set` and `g_count01338748` names through an inlined wrapper and a canonical-global expression; it uses the existing `BfmeN1242::rva008B8E10` declaration without a linker alias.

## Layout and ownership evidence

The complete actual array constructor at `0x008B9C60` calls the base initializer at `0x00899F00`, installs the array vtable, and clears fields `+0x20`, `+0x24` and `+0x28`. The complete array setter at `0x008B8E10` accepts a signed DWORD index followed by a value pointer, adjusts no receiver, and returns with `ret 8`. It calls reserve at `0x008B8D60` and tagged-store at `0x008B84C0`. The complete store reads the element array at `+0x20`, reads and writes an index-times-four slot, strips or adds the pointer's low tag bit, invokes incoming slot 0 and previous-value slot 4, and tests the AL result of incoming slot `+0x14`. The reserve helper allocates and copies four-byte slots. Thus the payload is a tagged value pointer and the indexing operation is a signed integer index; this conclusion does not rely on allocation size or a donor's class name. The exact identities of all possible dynamically selected value hooks are not claimed.

The complete value constructor at `0x008A9B00` reads and writes flags at `+4`, registers the object through capacity, count and entries at registry offsets 0, 4 and 8, installs its vtable, assigns the empty string block at `+8`, increments the block's 16-bit reference count and clears `+0x0C`. The target's input selection reads the type at `+4`, selects the direct value for tag 1 or the pointer at `+0x20` otherwise, then reads the string block at `+8`. The shared address `0x012D5298` is string data, not an installed owner vtable.

The complete assignment at `0x008A9A70` increments the source block's 16-bit reference count, releases the destination block at `+8`, conditionally invokes the pool free callback and installs the source block. Its parameter is the address of a one-pointer string view; it returns with `ret 4`. The complete 345-byte encoder at `0x008A0320` receives a DWORD code point through one thiscall stack argument and returns the receiver in EAX with `ret 4`. Its existing address-derived declaration is reused. The independently matched UTF-8 donor at `0x0089DF20` was read and completely decoded; its source is a shape donor, not evidence for the callback's owner.

The allocation and free operations are indirect calls. Their call sites pass one allocation-size DWORD and receive a pointer in EAX, pass storage plus size to headered free, or pass one string-block pointer to the pool's `+4` callback. The callers perform the corresponding cdecl cleanup. Existing canonical function-pointer declarations are reused; the dynamic allocator and pool callback implementation identities are not established by these sites. The integer index-store virtual calls are documented separately above and do not establish every dynamic target's identity.

All relevant complete small helper decodes and checked inventories are retained as `build/aa650-retry/008XXXXX-disasm.txt` and `008XXXXX-checked.txt`.
