# UTF-8 initialization at RVA 008A0320

The tested base is `37546667b555aebb95e03d0afd82848799c31380`. The source defines `EAStringC::UTF8_Initialize008A0320(int)`. The address suffix preserves uncertainty about EA's original method spelling. The behavior is initialization from one signed integer code point; this note does not identify the original method as `UTF8_Initialize` merely because an older bank used that name.

## Boundary and physical ABI

The complete retail body occupies `[0x008A0320, 0x008A0479)`, exactly 345 bytes. Its SHA-256 is `cae6d4688ba4c6fbe80c67f65346aa938dbb7b95ae81529229c8fbae379fc5d5`. The last instruction is the complete `ret 4` at `0x008A0476`; seven INT3 bytes separate it from the next body at `0x008A0480`. Every conditional branch and both unconditional jumps remain inside the body and land on decoded instruction boundaries. The four return instructions are at `0x008A03B8`, `0x008A03EE`, `0x008A0430` and `0x008A0476`. Each path returns the original receiver in EAX, without hidden return storage or a receiver adjustment. The target has no exception registration or unwind states and is not an object constructor. Container payload and constructor-unwind checks do not apply.

The receiver arrives in ECX and is retained in ESI. One four-byte integer argument is loaded from `[esp+0xC]` after two register saves. Signed comparisons against `0x80`, `0x800` and `0x10000`, and arithmetic right shifts, establish the signed transport used by the source. The implementation preserves retail's treatment of negative and out-of-Unicode-range integers rather than adding validation.

Both complete callers were decoded. At `0x008AA316`, the already matched 361-byte body at `0x008AA2B0` pushes the integer result from `AptValue::toInteger`, loads ECX with the address of a one-pointer stack string, and calls the target directly at `0x008AA320`. It performs no argument cleanup after that call and subsequently reads that string's storage for append and release. At `0x008AA815`, the complete 1219-byte body at `0x008AA650` pushes its decoded code point and loads ECX with another one-pointer stack string before the direct call at `0x008AA81F`. Both callers ignore EAX, so the reference spelling is an ABI-compatible expression of the target's witnessed return-this behavior, not an independently observed source-level distinction from a pointer return.

Retiring the generated ledger name made the unchanged matched `0x008AA2B0` caller's address-only `?d_008a0320@@YAXXZ` reference unresolved. That caller already casts the neutral function address to a one-argument thiscall member pointer. One compatibility pin retains that existing address binding to `0x008A0320`; it does not assert the cdecl/void transport encoded by the neutral placeholder spelling. Independent support is the complete target ABI and the actual instruction-aligned call at `0x008AA320`. `legacy-pin-before.log` records the absence of a pin before this repair; `caller-gate-python.log` now records both caller-file bodies passing after the repair, and `legacy-pin-after.log` records the pin consistency check. No caller source, extra real identity, thunk alias, or `_STL` name is introduced.

## Storage and actual calls

The target decrements a 16-bit reference count at storage offset zero, writes byte payload at offset eight, writes a 16-bit length at offset two, and clears the 16-bit word at offset six. Its reset stores the address of the shared empty block, not a vtable. The assignment's vtable screening hint at VA `0x012D5298` is therefore inapplicable. The existing matched datum `?g_rva012D5298Empty@@3VStringDataC@EAStringC@@A` supplies this canonical address and type spelling. The local `StringDataC` declaration describes the eight-byte header that the target uses; it does not claim the size of a heap allocation or of the 16-byte static sentinel. The bank's descriptive field names are retained.

The only direct call is at `0x008A038C`, directly to the complete 260-byte `EAStringC::ChangeBuffer` body at `0x0089E570`, not to a thunk. Its SHA-256 is `b36009e236c0de4ac3a85efdf8f755db1426ac0d2e8012c27cd3754a5805f117`. The five four-byte stack arguments, in source order, are reserve count, zero copy offset, the smaller of existing length and reserve count, push-zero value one, and the same copy length. ECX is the unadjusted string receiver. Both callee returns use `ret 20`. The complete callee reads reference count at offset zero, length at two, capacity at four and reset word at six, and copies character bytes beginning at eight. It returns no value used by this target. The source uses the existing private canonical declaration `?ChangeBuffer@EAStringC@@AAEXIIIW4CBPushZero@1@I@Z`.

The target's indirect release at `0x008A0334` loads the callback table through VA `0x01337A30`, calls its offset-four entry with the old header pointer, and explicitly removes four argument bytes afterward. This supports the existing cdecl `free(void *)` table view, not a virtual receiver call. The actual `ChangeBuffer` body independently uses the same table's offset-zero allocation callback and offset-four release callback with caller cleanup. No concrete runtime callback identity is invented. The canonical pool reference resolves through the existing `?g_bfmeStringPool1284@@3PAUBfmeStringPool3AF0@@A` address record.

The EA string family is supported by the unchanged receiver passed to the canonical `ChangeBuffer`, the matched EA string neighbors at `0x008A0480` and in the substring family, the shared datum's canonical `EAStringC::StringDataC` identity, and `ea_evidence.csv`'s independent `wb1-run` file attribution to `Libraries/Source/Apt/string/EAString.cpp`. No matching EAString source donor exists in the checked-in Zero Hour tree. The matched address-qualified encoder at `0x0089DDC0` is behavioral corroboration, not proof of this method's original name. Its complete 124-byte body was decoded and has four cdecl returns and no calls.

## New hypothesis and measured result

The saved preferred bank reproduced 334 emitted bytes, 267 in-range differing bytes and 11 missing bytes, for 278 wrong bytes over the verified extent. Its three-byte and four-byte continuation expressions omit masks present in the decoded retail instructions. Reintroducing those masks alone produced 343 bytes with 301 in-range differences and two missing bytes. Making the real non-inlined `ChangeBuffer` implementation visible did not alter either measured shape. Predecrement, inline release, inline finishing helpers and size-oriented flags did not solve the initial EDI zero-hoisting difference. Returning inline encoders removed that difference but merged the retail return paths; the best such pointer-return trial still had 135 in-range differences and 64 missing bytes.

The successful hypothesis was that the original control flow reset the offset-six word once after the encoding arms. Keeping the length stores in the individual arms and moving that reset to a common source tail let MSVC 7.1 duplicate the return tails without hoisting zero into EDI. This prediction would have been refuted by persistence of the `push edi` divergence at offset `0xC`, or by failure to reproduce all four retail return tails. The measured native tail shape emitted 345 bytes and left only a seven-byte adjacent scheduling difference at offsets `0x129` through `0x12F`. Moving the four-byte terminator store after the middle continuation expression removed that residue. The final source, including canonical global and private callee declarations, probes exactly over all 345 bytes. A masked probe alone remains insufficient; the scoped byte gate validates relocation destinations separately.
