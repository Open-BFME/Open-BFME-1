# BFME FVF record identities at RVA 0x00964150 and RVA 0x00964270

Retail refutes both Matrix3D ledger claims. The 26-byte body at RVA 0x00964270 is the existing pinned `BFMEVertexFVFInfo::BFMEVertexFVFInfo(unsigned, unsigned)`. The 274-byte body at RVA 0x00964150 initializes the same FVF record. Its EA member spelling is unproven, so the correction uses `void BFMEVertexFVFInfo::Rva00964150(unsigned, unsigned)` rather than guessing a descriptive member name. These are two separate bodies, a constructor and its initializer, with their existing extents preserved.

## Retail facts

`build/rlink/retail-probe.log` records the baseline path, its SHA-256, complete raw body bytes, decoded instructions, instruction-validated direct callers, the FVF format table, and the ILT search. The baseline SHA-256 agrees with `inputs/baselines/bfme1/retail-1.03-unpacked/manifest.json`. Every five-byte E9 entry in the initial ILT was read and its jump chain followed. No entry ends at either disputed body. The witnessed callers encode direct calls to these bodies, so assigning callers from a nearby or similarly named thunk would be incorrect.

At RVA 0x00964270, ECX is saved as the receiver. The two stack arguments are forwarded unchanged to RVA 0x00964150. The wrapper returns the receiver in EAX and ends with `ret 8`. At RVA 0x0091DCC1, the independently matched `VertexBufferClass` constructor calls this wrapper. Its preceding code allocates 0x40 bytes at RVA 0x0091DCA0, supplies the allocation as ECX, and pushes its unsigned FVF and explicit vertex-size arguments. Afterward it stores the result at receiver offset 0x14 and reads result offset 4 as the stride for the total vertex-byte count. `targets/game/reverse/symbols.csv` already pins `??0BFMEVertexFVFInfo@@QAE@II@Z` at RVA 0x00964270, and `game/Libraries/Source/WWVegas/WW3D2/dx8vertexbuffer.cpp` independently declares and calls that exact constructor.

At RVA 0x00964150, the first argument is stored directly at receiver offset 0. When it is nonzero it is passed by value to `_D3DXGetFVFVertexSize@4` at RVA 0x00A06403. When it is zero the second argument supplies offset 4. Neither argument is dereferenced as a Matrix3x3 or Vector3. The remaining stores use integer FVF tests: position bit 0x2, blended-position mask 0xC and last-beta flag 0x1000, normal bit 0x10, diffuse bit 0x40, and specular bit 0x80. The receiver offsets are FVF at 0, size at 4, location at 8, normal at 0xC, blend at 0x10, eight texture offsets at 0x14 through 0x30, diffuse at 0x34, and specular at 0x38. A final dword at 0x3C is initialized to 15 and replaced by the matching index in the 15-entry FVF table at VA 0x0113E0B8. The complete write extent is 0x40 bytes. This body ends with `ret 8` and has no constructor return of ECX in EAX.

The independently matched reset callers at RVA 0x0091DA30 and RVA 0x0091DAA0 call the initializer at RVA 0x0091DA7E and RVA 0x0091DAEE. Each supplies one FVF dword from VA 0x0113BD28, a zero second argument, and a receiver starting at VA 0x013467F0. The receiver advances by 0x40 until VA 0x01346BB0, proving fifteen instances of the same record. The existing pin `?bfmeResetXZ@BfmeDynElemXZ@@QAEXIH@Z` represents those calls with an invented slot type and a signed flag. The bytes and their use instead establish an FVF record and a vertex-size argument. The existing pin is retained as an additive historical candidate; corrected callers use the single canonical initializer identity.

`build/rlink/storage-probe.log` checks all DIR32 names and data rows within the slot extent and reads its virtual storage using `tools/reloc_ledger.py`'s PE-aware `Image`, which handles uninitialized section tails. ## Reference comparison and argument contract

Zero Hour's `inputs/reference/CnC_Generals_Zero_Hour/GeneralsMD/Code/Libraries/Source/WWVegas/WW3D2/dx8fvf.h` declares `FVFInfoClass(unsigned FVF, unsigned vertex_size=0)` with the same first fifteen dword fields. `dx8fvf.cpp` computes those fields in the same order with the same FVF tests and the nonzero-FVF versus explicit-size branch. BFME adds the dword at 0x3C and uses its witnessed texture-offset loop; this correction preserves those retail differences rather than substituting the reference implementation. Raw reference text is in `build/rlink/zh-dx8fvf-h.txt` and `build/rlink/zh-dx8fvf-cpp.txt`.

The receiver is a nonvirtual 0x40-byte FVF record. Both methods use the ECX member-call contract with two four-byte unsigned value arguments and callee stack cleanup of eight bytes. Only the wrapper returns the receiver. The initializer's member spelling is deliberately address-derived because neither the reference nor an EA string supplies BFME's reset-method name. `build/rlink/name-oracle-fvf.log` records the absence of a witnessed layout name for this local shim.

Zero Hour's `WWMath/matrix3d.h` instead stores three Vector4 rows, totaling 0x30 bytes. `WWMath/matrix3d.cpp`'s `Set(const Matrix3x3&, const Vector3&)` dereferences the two arguments and copies twelve floats. `build/rlink/zh-matrix3d-contract.txt` and `build/rlink/zh-matrix3d-set.txt` capture that contract. `build/rlink/actual-matrix3d-body.log` shows the already pinned actual Matrix3D setter at RVA 0x008D6710 reading the two referenced objects and writing only through receiver offset 0x2C. Thus neither FVF body can retain the prior Matrix3D identity.

## Scope and refutation

The correction retypes the initializer in its existing `game/Libraries/Source/WWVegas/WWMath/Matrix3D_Set_Thunk.cpp` translation unit and reconstructs the body in real C++ while preserving all 274 retail bytes and the existing compiler flags. The constructor remains in `game/Libraries/Source/WWVegas/WW3D2/boxrobj.cpp` under its existing compiler flags. Its receiver and arguments are retyped to the pinned FVF contract, and its initializer remains a member call. The genuine Matrix3D geometry uses and included reference header are preserved. The three local dynamic-slot declarations and their calls are retyped to the pinned FVF receiver, and the existing datum is retyped without changing its address, size, or bytes. No inheritance, additional forwarding function, shared header, generated source, or alias identity is introduced. Existing pins remain additive.

A changed instruction in either disputed body or any caller would refute byte preservation. An actual thunk chain ending elsewhere than reported would refute the caller routing. A receiver allocation or array stride other than 0x40, reference arguments dereferenced as rotation and translation, or a caller interpreting the object as twelve floats would refute the FVF identity. An independently witnessed EA member spelling would replace the initializer's address-derived method name. Scoped gate outputs and the final changed paths are recorded in `build/worker-final.md`. This run retains its raw commands, receipts, byte comparisons and gates in `build/rlink/run-1791146831/`.
