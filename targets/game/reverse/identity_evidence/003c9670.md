# 0x003C9670 constructor: the 0x58-byte region container, not LivingWorldRegion

The 255-byte constructor at 0x003C9670 was claimed as
`??0LivingWorldRegion@@QAE@ABVAsciiString@@@Z`. The row had no evidence
column, and the retail image contradicts it.

- Its only caller (tools/callers_of.py) is the "LivingWorldRegionCampaign" INI
  block parser 0x003C9B60. That parser pushes 0x58 to operator new, calls this
  constructor through ILT 0x0004602E, and passes the result to
  INI::initFromINI with the field table at VA 0x010EDC48.
- Entry #0 of that table is the "Region" keyword with parser ILT 0x0002202A ->
  0x003C9980. That parser allocates 0xF4 bytes, constructs them through
  ILT 0x00008CC4 -> 0x0061AF80, and appends the pointer to the vector at
  instance+0x30. The instance is the 0x58-byte object this constructor builds.
- 0x0061AF80 installs vtable 0x01117258, which is pinned as
  `??_7LivingWorldRegion@@6B@`. Its destructor 0x0061A780 is
  `??1LivingWorldRegion@@UAE@XZ`. The landed LivingWorldRegionManager
  bodies (0x003C8A50, 0x003C8C60) model LivingWorldRegion* elements at
  campaign+0x30.

So the 0x58-byte object holds the regions: it is the container that the
"LivingWorldRegionCampaign" block creates, and it is not a LivingWorldRegion.
It also has no vtable, because the constructor stores a string at +0, while
the 0xF4 class installs one. The same class name therefore cannot cover both.
No string, vtable or caller names the container's C++ class. The row takes
the address-derived `??0Rva003C9670@@QAE@ABVAsciiString@@@Z`. Its TU member
at +0x30 was named `m_effects`, but the Region parser proves that slot holds
the 0xF4-byte objects, so it becomes `m_vector30`. The +0x2C member was named
after ConqueredEffectEvenglow, but that table entry parses at offset 0 with its
key as userData, so the member becomes `m_string2C`. Probe: 255/255 exact
outside relocations.
