# RVA 0x001BBC50: complete query attempt and native lifetime

## Result and reopening condition

This is a measured partial at revision 53fe54db1c62eebdd204a076d1eb81b7ffe4664e. No source recovery or identity rename is claimed. The preferred candidate is `build/001bbc50/28-terrain-declaration.cpp`, which retains the existing `Rva002C12E0Locomotor::locoQuery` name. Its raw probe is `build/001bbc50/28-terrain-declaration.probe.log`. All numbered trial sources, raw probe outputs, decoded bodies and checked-callee outputs remain under `build/001bbc50/`. A retry needs a concrete explanation for retail spilling the bird pointer before its null test and retaining the later turn boolean in BL, or a native declaration that changes this allocation. Merely repeating `register`, changing the boolean to unsigned char, or changing the boolean assignment to an explicit branch has already produced identical instructions.

The new hypothesis was that independently decoded native GeometryInfo construction and cleanup could preserve the owning temporary without editing its smaller canonical header or privately redeclaring GeometryInfo. The address-derived lifetime adapter calls the actual copy and destruction thunks on correctly sized aligned storage. This produced the first complete measured candidate for this target. The hypothesis would fail if the copy wrote beyond the storage, an unwind state required another local owner, a cleanup used a different receiver, or the complete body could not be compiled. These tests did not refute the storage and lifetime experiment. They do not establish that the adapter is an accepted canonical declaration for landing. That declaration question remains unresolved.

## Native GeometryInfo payloads and exception cleanup

Copy constructor 0x000FFD10 is completely decoded. It initializes the vtable at +0x00, copies the byte at +0x04, copies every four-byte field from +0x08 through +0x28, constructs the shape vector at +0x2C through thunk 0x00027570, constructs the record vector at +0x38 through thunk 0x000149DE and copies every four-byte field from +0x44 through +0x58. It returns the receiver in EAX and cleans its source-reference argument with `ret 4`. These writes independently require 0x5C bytes. The target uses the native copied float at +0x14. Allocation size and donor names were not used to infer either vector's payload.

The complete shape vector copy at 0x000FDE60 and value copy at 0x000FCED0 show seven four-byte fields at offsets +0x00 through +0x18, the owning string copy at +0x1C and a byte at +0x20 in each 0x24-byte element. The complete record vector copy at 0x000FDF90 and value construction at 0x000FD650 show three four-byte fields at +0x00, +0x04 and +0x08 and an owning string copy at +0x0C in each 0x10-byte element. No scalar meanings, pair type or key type is inferred from those raw fields. Complete string copy 0x00887B60 copies the buffer pointer and increments its reference count. Complete release helper 0x00887940 decrements the reference count, frees a zero-count buffer and clears the pointer. Their decoded bodies, rather than the ledger's library aliases, establish ownership.

Normal destructor 0x000FFCA0 destroys the record vector at +0x38, then the shape vector at +0x2C, then writes the Snapshot vtable. Shape destruction at 0x000FF700 releases each element's +0x1C string with stride 0x24; record destruction at 0x000FF7D0 releases each +0x0C string with stride 0x10. Both check all normal return paths and release their vector allocation. Their exceptional base cleanup bodies 0x000FD390 and 0x000FD420 also decode completely and free the allocation using the respective strides. Snapshot cleanup 0x0005C520 only writes its vtable and returns.

The target's single unwind state destroys the local through thunk 0x000309F4, using `[ebp-0x68]`. The copy constructor's unwind states clean Snapshot, then the successfully constructed shape vector; the normal destructor's unwind states agree with these receiver adjustments. The vector destructor unwind actions free their bases at 0x000FD390 and 0x000FD420. Raw inventories are `0x001BBC50-eh.log`, `0x000FFD10-eh.log`, `0x000FFCA0-eh.log`, `0x000FF700-eh.log` and `0x000FF7D0-eh.log`. No STL ledger row or pin was added or changed. The adapter preserves calls into these native owners; it does not substitute a trivial copy or suppress their destruction.
