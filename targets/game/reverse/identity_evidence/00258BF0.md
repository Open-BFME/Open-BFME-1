# 0x00258BF0: CashHackSpecialPowerModuleData::Upgrades vector overflow, not ICoord2D

The 305-byte thiscall body at 0x00258BF0 (ret 0x14) is a matched row named
`?_M_insert_overflow@?$vector@UICoord2D@@...` sourced from a `__emit` thunk
(`VectorICoord2DInsertOverflowThunk.cpp`). The element width is eight bytes:
the size arithmetic divides by eight twice (`sar eax,3`), so ICoord2D (an
`int x; int y` pair) and `CashHackSpecialPowerModuleData::Upgrades`
(`ScienceType m_science; Int m_amountToSteal` per upstream
`GeneralsMD/Code/GameEngine/Include/GameLogic/Module/CashHackSpecialPower.h`)
are both width-compatible, and width alone cannot decide.

- tools/callers_of.py finds exactly two callers, both in
  `CashHackSpecialPower.cpp`: `?push_back@?$vector@UUpgrades@
  CashHackSpecialPowerModuleData@@...` at 0x00258EC0 and
  `?parseCashHackUpgradePair@@YAXPAVINI@@PAX1PBX@Z` at 0x00258F10.
  No ICoord2D caller reaches this body anywhere in retail.
- The 5-byte ILT at 0x0000EF11 jumps straight to 0x00258BF0 and already
  carries the Upgrades name
  (`?_M_insert_overflow@?$vector@UUpgrades@CashHackSpecialPowerModuleData@@...`);
  the typed push_back at 0x00258EC0 calls through it. The Upgrades identity
  is the one the callers type.
- The same 305-byte shape is already matched as the Upgrades overflow of the
  sibling OCL specialization at 0x00262FE0
  (`OCLUpgradesVectorInsert.cpp`), whose element is likewise two ints.
  That row landed as `?dup_003f8ef0` with the real overflow name in
  `object-symbol ... C++ alias`; this body follows the same alias pattern.
- Probe: native `_STL::vector<CashHackSpecialPowerModuleData::Upgrades>`
  anchor TU compiles the named `_M_insert_overflow` 305/305 EXACT (modulo
  relocation slots) against 0x00258BF0.

The body is therefore the CashHack Upgrades overflow. The old ICoord2D name
is retired; the row is claimed from the CashHack TU. Probe: 305/305 exact.
