# RVA 0x007E5080: VP6 player open

The source retains the bank's `Rva007E5080Vp6Player::open` identity and address-derived stream names. The original BFME derived player class name remains unknown. The tested base revision is `dbfea2ff0cfbd7707f89cdc5cea96c69a4446798`. The binary evidence is the current retail baseline, not the older Ghidra image.

The retry hypothesis was that the landed constructor at RVA 0x007E3B40 and the landed stream methods supplied the ABI evidence missing from the bank. Its refutation condition was that using those declarations, with the decoded target control flow, failed to improve the measured reconstruction. The unchanged bank was measured first at the full retail extent. Raw experiments, complete disassemblies and checked-callee outputs are retained under `build/vp6-open-007e5080/`.

## Boundary and incoming ABI

`target-disassembly.log` decodes every instruction from RVA 0x007E5080 through the final `ret 8` at RVA 0x007E535E. All conditional branches and direct jumps remain inside that extent, and every normal return reaches the same complete epilogue. The following bytes are alignment rather than a missing continuation. `checked-target.log` records the complete direct-callee inventory.

The complete matched caller at RVA 0x0040E3B0 is decoded in `caller-and-lifetime.log`; `checked-caller.log` checks its full extent. At RVA 0x0040E3F3 it pushes the four-byte flags value, constructs a four-byte by-value AsciiString beneath it through StringBase<char> at RVA 0x00887B60, loads TheVideoPlayer into ECX, and calls virtual slot +0x30 at RVA 0x0040E40D. It stores the full EAX result as a stream pointer. `vtable-player.log` identifies that slot of the table installed by the adjacent player-family bodies as ILT RVA 0x000231FF, which jumps to the target. This establishes receiver position, argument order, widths, by-value ownership and pointer return without hidden return storage. The target releases its AsciiString parameter on both the early and common exit paths.

The target calls player slot +0x4C with one copied AsciiString. The table route leads to the independently decoded `VideoPlayer::getVideo` at RVA 0x0081CD70, which has `ret 4`, returns an entry pointer in EAX and destroys its by-value input. Its complete comparison loop uses the native Video record. The reconstruction includes the canonical Video header and retains `Rva007E5080Vp6Video` as a typedef, rather than inventing another Video layout. It reads only that record's filename at offset zero.

## Exception cleanup and remaining data views

`eh-target.log` decodes the target's three unwind states. State zero destroys the by-value string at frame +4. State one destroys the local filename at frame -0x214. State two frees the pending allocation from frame -0x210 through operator delete at RVA 0x00881EB0. Both string cleanup actions route through ILT RVA 0x0000D828 and the AsciiString destructor at RVA 0x0005EE90 to StringBase<char>::releaseBuffer at RVA 0x00887940. `eh-object.log` follows the compiled handler's relocation graph through its FuncInfo, unwind map and actions for comparison with those adjustments and destinations.

`eh-ctor.log` decodes the constructor's sole unwind state. Its cleanup at RVA 0x00C544D0 reloads the saved receiver and calls the base destructor at RVA 0x0081E4B0. The complete base destructor consumes ECX without stack arguments. The caller's failed-construction cleanup is global delete, consistent with the actual allocation and constructor path. No container or element destructor is inferred from allocation size.

The StringBase copy, C-string construction, format and release helpers are fully decoded in `abi-helpers-disassembly.log`. They support the canonical four-byte AsciiString and its allocation header, not the unrelated aliases listed at the same addresses. The canonical header preserves the inline forwarding construction and destruction needed at by-value call sites. Debug::Format at RVA 0x008895F0 takes its receiver on the cdecl stack and writes through that receiver with a 0x1FF limit; the existing debug header establishes its 512-byte buffer and inline output forwarder. The reconstruction uses that buffer and returns the original report receiver from the forwarding overload. Its temporary has no ownership cleanup.

The landed movie initializer at RVA 0x007E4D40 writes enable bytes at VA 0x01309848, 0x0130998D and 0x01309AD2, filenames one byte after each, and labels at each filename +0x104. Those stores and the decoded target stride establish three 325-byte path records with a one-byte flag, 260-byte filename and 64-byte label. The reconstruction indexes that record, then reads the enable byte immediately preceding its filename. It skips disabled records rather than terminating the search. The no-video debug chain and failed-file debug call preserve their decoded vtable slots, argument order and original bank names. The retained GlobalData declaration is only a byte view for the bank's flag at +0xA7D; it constructs no GlobalData and claims no additional layout.

## Experiments and acceptance

The original bank and every subsequent trial source are retained with unedited probe output. The unchanged bank measured 705 bytes, 534 masked-byte differences and 27 displaced relocation sites. The 16-choice EH search in `eh02.search.log` and its referenced `build/shape_search/` manifest yielded one unchanged instruction shape. The source-family generator found no applicable automatic loop, branch or frame choice. Explicit pointer-bound iteration, an independently stored initial result and an early-return restructuring failed to reproduce the target. The useful changes were the canonical string forwarding, the verified stream constructor and virtual ABI, native diagnostic forwarding and temporary lifetime, the indexed path record with its prefix flag, and a named boolean local after allocation. Trial 18 is the first full 737-byte relocation-masked match. Adoption of the canonical Video header preserves that result.

Strict relocation verification passes in `add-match.log` and again in `gate-bash.log` after final source normalization. The scoped gate verifies all 737 bytes, five string references, thirteen DIR32 references and the source claim. Source declaration, naming, class adoption and pin consistency outputs are retained separately in this task's build folder. The naming CLI accepts Git revisions, so `check_names.py` calls its unchanged regression validator on the preserved bank and final source; `name-regression-final.log` records zero regressions. No shared header, tooling, STL ledger name or STL pin is changed. This C++ source change requires the scoped gate; it does not trigger a header or shim full gate.

The normal `check_csv.py` invocation in `check-csv-final.log` cannot complete before collection: its Git catalog still contains the automatically retired bank and does not include the untracked new source. This checkout prohibits staging. `check_projected_catalog.py` supplies only those intended catalog additions and deletion to every unchanged checker validator; `projected-csv.log` records zero problems. The coordinator must stage the explicit handoff paths and rerun the normal checker and commit hooks before accepting collection. This procedural check remains pending despite the passing byte gate.

A complete caller with a different stack contract, a vtable route to a different body, an outgoing target branch, a different constructor cleanup owner, a payload access inconsistent with the included Video declaration, or a strict relocation failure would refute the corresponding claim and prevent collection. The original derived player class name remains unresolved and address-derived; that uncertainty is not presented as a recovered real class identity.
