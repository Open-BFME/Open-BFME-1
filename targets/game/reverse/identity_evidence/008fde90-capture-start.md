# Capture-start boundary and ABI evidence

The recovery keeps the address-derived symbol `?Rva008FDE90StartMovieCapture@@YAXPBDMH_N@Z`. The surviving WW3D source explains the capture behaviour, but its two-argument declaration does not describe this retail ABI. No original function or owner identity is claimed.

## Boundary

Complete instruction decoding of the original ledger range finds the target's sole return at RVA `0x008FDF7E`, followed by `INT3` at `0x008FDF7F`. Every conditional branch originating at `0x008FDE90` stays in the half-open range `[0x008FDE90, 0x008FDF7F)`. There is no outgoing tail jump. The next aligned body starts at `0x008FDF80`. It has returns at `0x008FDFAC` and `0x008FDFCB`; its non-capturing path calls `0x008FDE90` and then removes sixteen argument bytes. Thus the previous 316-byte row combined the capture-start body, its padding and a separate caller. A branch from the first body into the second, or an instruction decoding differently in the reference image, would refute this boundary correction.

## Arguments and ownership

The independent caller passes four stack slots without a receiver or hidden result pointer. In the target, slot one supplies the filename, slot two is loaded as a 32-bit x87 float, slot three is passed as the buffer count, and slot four is passed as the compression flag. The caller discards the result; the target leaves the constructor result in EAX after storing it in the movie global. The reconstruction exposes no consumed return value.

The complete constructor at RVA `0x00958200`, already recovered in `Rva00958200BfmeThingTXACtor.cpp`, receives ECX as the allocation and seven stack slots. Every return uses `ret 0x1c` and returns ECX's saved value in EAX. The filename reaches `sprintf` and the file-opening call. Width and height reach both the image-size calculation and `SetRect`; bit count reaches the calculation and the bitmap header's word field; frame rate is loaded as a float and converted for the AVI rate; count is stored at object offset `+0x08` and multiplies the buffer allocation; compression is tested as a byte. The target supplies width and height from the four LONG fields written by the `GetWindowRect@8` import, bit count 24, and its final three arguments in their observed order.

The constructor writes the vtable at `+0x00`, image size at `+0x04`, count at `+0x08`, buffer pointer at `+0x0c`, counters at `+0x10` and `+0x14`, AVI file at `+0x18` and stream at `+0x1c`. These accesses establish the complete allocation view independently of its 32-byte allocation size. The recovery reuses the existing constructor's address-derived `BfmeThingTXA` declaration and member names; it adds no shared declaration. One additive pin connects that existing constructor object symbol to its independently decoded direct target at `0x00958200`. The first scoped gate rejected this constructor call because the existing ledger stores its true object name in a note rather than as its row name. The pin fixes this resolver input without changing the callee identity or declaration.

The vtable installed by that constructor is VA `0x0113DEE4`. Its sole function slot points directly to RVA `0x00958680`, whose complete deleting-destructor body flushes buffered frames, releases the stream and file, deletes the buffer array, tests flag bit zero and conditionally calls scalar operator delete on the unadjusted receiver. It returns the receiver in EAX and removes one four-byte flag slot. The target's virtual deletion passes flag one and the original movie pointer. The non-deleting destructor at `0x00958640` confirms the same field cleanup without freeing the receiver. The original class name is not inferred from these facts.

## Constructor failure

The retail EH handler at RVA `0x00C5ABAB` loads FuncInfo at `0x00E49C04`. Its single unwind state transitions from zero to minus one and invokes the complete eleven-byte action at `0x00C5ABA0`. That action loads the allocation from `[ebp-0x20]` and calls the already matched scalar operator delete at `0x00881EB0`. It does not invoke the object's destructor. The emitted object's state map has the same predecessor and one action; that action has the same concrete instruction bytes, the same frame slot and the scalar-delete relocation. This verifies construction-failure ownership separately from the main-body match. A different state count, cleanup slot, deallocator or receiver adjustment would refute this reconstruction.

## Measured evidence

The first complete four-argument candidate emits the decoded target extent exactly outside relocation slots. Probing the original ledger size shows zero differing emitted concrete bytes and seventy-seven bytes beyond the compiled body. Changing the rectangle fields from 32-bit int to native LONG preserves the exact result. The next scoped gate required the already recorded private WW3D global spellings. The final source includes the existing `ww3d.h` after preloading its dependencies and inserts one friend declaration in that header only for this translation unit. Preprocessing verifies that the declaration occurs exactly once, inside WW3D. No class data layout, shared header or shared policy changes. Two earlier header-access template trials failed with MSVC 7.1 internal compiler errors and were rejected. The generated EH choices search reaches exact shape at trial zero; no register or x87 experiments are required.
